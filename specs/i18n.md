# Language Support (i18n)

**Status:** draft

## User story

As a user in Brazil or the US, I want ShelfSense's interface in my own language, so that I can use the app comfortably without translating it in my head.

## Acceptance criteria

- [ ] Given a user's device/browser locale is Portuguese (Brazil), when they open the app for the first time, then the UI renders in Portuguese (Brazil) (`pt-BR`).
- [ ] Given a user's device/browser locale is anything other than `pt-BR` (including English or an unsupported locale), when they open the app for the first time, then the UI renders in English (US) (`en-US`) as the fallback.
- [ ] Given a user opens Settings, when they select a different language, then the whole app immediately re-renders in that language and the choice persists across restarts (overriding auto-detection from then on).
- [ ] Given a UI string exists anywhere in the app, when it's displayed, then it comes from a translation key — no hardcoded user-facing text in component code.
- [ ] Given a translation key is missing a `pt-BR` value, when the UI renders it in Portuguese, then it falls back to the `en-US` value rather than showing the raw key or blank text.
- [ ] Given a developer adds a new UI string, when they commit it, then the key + English value are added immediately; the `pt-BR` value may follow afterward (English is the source of truth keys are authored against — matches the original intent of this spec).
- [ ] Given a date, quantity, or other localizable value is displayed (e.g. a product's `expires_on`), when rendered, then it uses locale-aware formatting (see Non-functional) — not a hardcoded format.

## Data

**Locales at launch:** `en-US` (default/fallback), `pt-BR`. (BCP 47 tags — matches what's already informally used: "English US" / "Português do Brasil".)

**Where translations live:** suggest a shared `packages/i18n` — locale JSON files (`en-US.json`, `pt-BR.json`) plus a thin loader — rather than duplicating strings separately in `apps/web` and `apps/mobile`. Shared vocabulary (e.g. "Save", "Cancel", the stock-status labels below) gets translated once; app-specific strings live under their own key namespace in the same files. `apps/api` only needs this if it returns user-facing text directly (error messages, notification bodies) — flag this when it comes up, not decided here.

**Key shape**, sketch:

```json
// en-US.json
{
  "common.save": "Save",
  "common.cancel": "Cancel",
  "stockStatus.inStock": "In stock",
  "stockStatus.low": "Low stock",
  "stockStatus.out": "Out of stock",
  "stockStatus.incoming": "Incoming",
  "inventory.expiresOn": "Expires {date}"
}
```

**Existing code this touches:** `packages/design-system`'s `StatusBadge` component (`packages/design-system/src/components/StatusBadge/StatusBadge.tsx`) currently has hardcoded English defaults — `"In stock"`, `"Low stock"`, `"Out of stock"`, `"Incoming"` — used whenever a consumer doesn't pass an explicit `label` prop. Since `shelf-sense-ds` itself has no locale awareness (and per its own conventions shouldn't grow app-specific concerns), **every consumer must pass a translated `label` explicitly** rather than relying on the component's default — worth calling out to whoever implements this, since it's an easy thing to miss and end up with English badges inside an otherwise-translated Portuguese screen.

## UI requirements

- **Settings screen** (`apps/web` only for now — owned by `specs/Settings.md`, which builds the page and hosts this picker as one of its `User Preferences` fields): a language picker (English (US) / Português do Brasil), defaulting to whichever is currently active. Selecting one switches the app immediately and persists the choice via `PATCH /preferences`'s `language` field (`apps/api`, Postgres) — supersedes this bullet's original `localStorage`/on-device-SQLite suggestion now that `specs/Settings.md` introduced one shared `preferences` table for every global preference, language included. No `apps/mobile` equivalent exists yet — see `specs/Settings.md`'s own Non-functional section on why.
- **First-launch detection**: read the device/browser locale, match it to `pt-BR` if exact, else fall back to `en-US` — no locale picker interrupts first launch; Settings is where a user corrects it if the auto-detected choice is wrong.
- No new `shelf-sense-ds` components needed for this feature itself (a language picker can be built from existing `Select`/`Button`) — but see the `StatusBadge` note above, which affects how *existing* components get used correctly, not what gets built new.

## Non-functional

- **Locale-aware formatting**, not just string translation: dates (`expires_on` renders `08/20/2026` in `en-US` vs `20/08/2026` in `pt-BR`), and any decimal quantities (`en-US` uses `.` as the decimal separator, `pt-BR` uses `,`). Use the platform's built-in `Intl` APIs (`Intl.DateTimeFormat`, `Intl.NumberFormat`) rather than hand-rolling format strings.
- **Text length**: Portuguese strings commonly run 15–30% longer than their English equivalents — UI built/reviewed only against English text is likely to truncate or wrap awkwardly once translated. Worth a Portuguese pass during UI review, not just a translation-correctness pass.
- **Bundle/startup cost**: only load the active locale's translation file at startup, not both — avoids shipping unused translations to every user.
- **Accessibility**: the active language should be reflected in the platform's accessibility locale (web: `<html lang>`; mobile: platform accessibility APIs) so screen readers use correct pronunciation.

## Out of scope

- **Locale-correct date *input*** (as opposed to date display, which this spec does cover) — native `<input type="date">` follows the visiting browser's own UI language, not this app's chosen locale, and nothing at the app/JS level can override that. See `specs/BACKLOG.md`.
- Languages beyond `en-US`/`pt-BR` — this spec covers the two-language launch only; adding a third language later shouldn't require re-architecting, but isn't being built now.
- Right-to-left layout support — not needed for either launch language.
- Machine/on-the-fly translation — all strings are human-authored and reviewed per language, not generated dynamically.
- Translating content that originates as user data (e.g. a product's own name/description entered by the user) — this spec covers the app's own UI strings, not user-generated content.
